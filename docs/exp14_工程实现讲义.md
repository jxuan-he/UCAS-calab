## 1. 先明确实验边界和预习内容

### 1.1 exp14 要解决什么

exp13 的 SRAM 环境基本允许 CPU 作如下假设：本拍给地址，下一拍就有返回数据。

exp14 要去掉这个假设。外部可能连续多拍不接收地址，也可能接收地址后过很多拍才返回结果。CPU 必须在这些等待期间保持正确，不能重复请求、丢返回数据、把返回数据配给错误的指令。

本实验的两个正式目标是：

- 将 CPU 对外接口改为类 SRAM 接口。
- 在带握手的 block RAM 环境中通过 exp14 func 的随机延迟功能验证。

验证目录从 `soc_bram` 换成 `soc_hs_bram`。AXI 转接桥属于 exp15，本次无需设计 AXI 五通道。

### 1.3 本次工作的核心问题

每遇到一个动作，问自己四件事：

1. 这个动作是持续的状态，还是只发生一次的事件？
2. 它完成之后，结果保存在哪里？
3. 下一级不接收时，哪些内容必须保持？
4. 被冲刷时，是指令无效了，还是外部事务也真的结束了？

能回答这四个问题，比先写出一大段 `always` 更有帮助。

## 2. 把教材映射到你们的 CPU

### 2.1 当前结构

```text
IF1             IF2               ID               EXE              MEM              WB
维护取指 PC  ->  接收指令      ->  译码/寄存器   ->  运算/分支      -> 接收访存数据  -> 写回
发取指请求       缓存给 ID         冲突检测          发数据请求         保存乘法结果     load 抽取扩展
```

教材的 pre-IF 大致对应你们的 IF1，教材的 IF 对应你们的 IF2；数据侧的 EXE/MEM 可以直接对应。无需为了贴合教材而把六级改成五级。

### 2.2 现有代码中要取消的“固定延迟假设”

| 当前定位 | 原有含义 | exp14 应重新定义的含义 |
| --- | --- | --- |
| `IF_PC.v`：`inst_sram_en = resetn` | 取指常开，重复读 RAM 可以丢弃 | 每次成功握手都会产生一次必须处理的返回，不能常开乱发 |
| 顶层：`if1_fire = inst_sram_en && if2_allowin` | CPU 自己认为本拍发出了请求 | 必须以 `req && addr_ok` 为外部接收事件 |
| 顶层：`if1_fire_r` 选择 `inst_sram_rdata` | 发请求后一拍，指令就回来了 | 指令只在对应 `data_ok` 时可信 |
| 顶层：`exe_ready_go = ~exe_is_div | div_done` | EXE 只会因为除法等待 | load/store 还需要等待地址请求被接收 |
| 顶层：`mem_ready_go = 1'b1` | MEM 总能立即前进 | 有外部事务的指令必须等响应 |
| 顶层：`exe_br_taken` 由 `exe_valid` 门控 | EXE 通常能及时向后推进 | MEM 阻塞时，分支不能冲刷后把自己丢掉 |

### 2.3 原有设计中可以保留的基础

你们有几项设计很适合继续使用：

- `allowin / ready_go / fire` 控制框架。
- load 统一在 WB 抽取、扩展并写回，MEM 不前递 load 数据。
- CSR 的读写和异常提交位于 WB。
- `older_redirect_pending` 检查 MEM/WB 中更老的异常或 `ertn`，用于限制年轻指令的外部副作用。
- 字节/半字 store 的写数据复制和字节使能生成。

但“保留框架”不代表只改一个 `mem_ready_go` 就完成。一次等待会把原先不可能发生的级间组合暴露出来，尤其是 EXE 分支和除法结果。

## 3. 用两次事件理解一笔事务

### 3.1 接口要表达两件不同的事

```verilog
addr_fire = req && addr_ok;  // 在时钟上升沿，请求被外部接收
resp_fire = waiting && data_ok; // 已有待响应事务，本拍收到响应
```

这里的 `waiting` 是 CPU 自己保存的事务状态。`addr_ok=1` 单独出现不代表发出了请求；`req=1` 单独出现也不代表外部接收了请求。

对读事务，地址握手表示“外部收下读请求”，响应表示“读数据有效”。对写事务，地址握手表示“写地址和写数据都被收下”，响应表示“这笔写事务完成”。CPU 一旦看到地址握手，就必须认为事务可能已产生不可撤销的作用，不能指望后续冲刷撤回写入。

### 3.2 一笔慢速 load 的逐拍例子

下表的握手动作都发生在对应拍末的上升沿。

| 拍 | `req` | `addr_ok` | `data_ok` | CPU 应做什么 |
| --- | --- | --- | --- | --- |
| T0 | 1 | 0 | 0 | EXE 保持当前 load 和请求信息 |
| T1 | 1 | 0 | 0 | 继续等待，不能让 load 提前进入 MEM |
| T2 | 1 | 1 | 0 | 请求被接收；把 load 的上下文送入 MEM |
| T3 | 0 | 任意 | 0 | MEM 等待，不重复发这笔请求 |
| T4 | 0 | 任意 | 0 | 同上 |
| T5 | 0 | 任意 | 1 | 接收这笔 load 的数据，送入 WB 的数据寄存器 |
| T6 | 0 | 任意 | 0 | WB 完成抽取、扩展和写回 |

### 3.3 一定要分开的三种 valid

| 概念 | 例子 | 被冲刷后是否一定为 0 |
| --- | --- | --- |
| 指令有效 | 这条取回的指令能否进入 ID | 是 |
| 外部事务未完成 | 取指地址已接收，指令还未返回 | 否，可能必须继续等 |
| 返回缓存有效 | 指令已返回，暂时存着等 ID | 可以清除 |

不要用一个含义模糊的 `valid` 同时替代三件事。变量数量不是越少越好，能否清楚表达状态才重要。

### 3.4 两条协议边界

教材规定：类 SRAM 接口允许在 `req=1 && addr_ok=0` 时修改请求内容。未被接收的错误路径请求可以撤换；握手完成的请求不能靠撤掉 `req` 取消。

类 SRAM 没有响应侧的 `ready`。外部不会因为 ID 或 WB 不接收，就替你保持 `data_ok` 和 `rdata`。你必须事先确保能消费或保存响应。

“无随机延迟”也不是“新请求和自己的响应在同一个上升沿完成”。本地 `sram_wrap.v` 通过 `ram_en_r` 返回响应，confreg 也通过寄存的请求返回响应，最早是接收请求之后的下一周期。下面的基础方案按这一环境设计；不要把它宣称成支持任意零周期组合返回的通用主接口。

## 4. 先决定实现策略

### 4.1 推荐的第一版

**指令端最多一笔未响应事务，数据端最多一笔未响应事务。两端相互独立，可以各有一笔。**

取指请求被接收后，直到这笔响应返回，不再发第二笔取指；返回指令缓存还未交给 ID 时，也暂不发下一笔。数据端先采用更保守的规则：只有 MEM 空闲时，EXE 的 load/store 才能请求。

这样不需要 FIFO、不需要事务 ID、不需要一组复杂的 outstanding 计数。吞吐率会下降，但更容易先证明正确。该限制不是教材强制要求，是本讲义为第一次实现选择的工程方案。

### 4.2 第一版先放弃哪些优化

- 不在取指响应返回的同拍发起下一笔取指。
- 不让尚未分配到接收槽的请求提前被外部接收。
- 不恢复 MEM 到 ID 的 load 前递。
- 不一开始就追求过去的 100 MHz 指标。

先完成正确性，再考虑缓存旁路、同拍出入和预取。每多开放一个并行行为，就要重新回答：返回归谁、空间是否足够、冲刷要丢几笔。

### 4.3 开写前先写下四条不变量

1. 每个端口的“已接收请求数 - 已处理响应数”始终是 0 或 1。
2. 每次响应都能找到唯一的请求上下文；没有上下文时不能把接口数据当有效结果。
3. 错误路径请求可以仍在等待，但其返回绝不能进入 ID。
4. 一条正常 load/store 只有在地址握手后才能进入 MEM，只有在响应后才能进入 WB。

这里“已处理响应”包括正常使用和冲刷后丢弃两种处理。

## 5. 接口怎么改，哪些编码不能照搬

### 5.1 顶层端口以实际 SoC 实例为准

本地 exp14 的 `soc_lite_top.v` 已给出了 CPU 端口名称。指令端需要：

| 方向（相对 CPU） | 信号 | 位宽 | 生成或使用方式 |
| --- | --- | --- | --- |
| 输出 | `inst_sram_req` | 1 | 取指控制器决定是否申请请求 |
| 输出 | `inst_sram_wr` | 1 | 恒 0 |
| 输出 | `inst_sram_size` | 2 | 恒 `2'd2`，一次取 4 字节 |
| 输出 | `inst_sram_wstrb` | 4 | 恒 0 |
| 输出 | `inst_sram_addr` | 32 | 本次准备请求的 PC |
| 输出 | `inst_sram_wdata` | 32 | 恒 0 |
| 输入 | `inst_sram_addr_ok` | 1 | 与 req 合成地址接收事件 |
| 输入 | `inst_sram_data_ok` | 1 | 表示一笔取指响应返回 |
| 输入 | `inst_sram_rdata` | 32 | 仅在响应时采样 |

数据端有对应的 `data_sram_*` 九个信号。`wr` 表示是否 store，`wstrb` 是 4 位字节使能。原有 `*_sram_en` 和 `*_sram_we` 不应直接保留为新协议的最终控制。

### 5.2 内部 mem_size 和外部 size 编码不同

这是你们代码里最容易直接接错的一处。

| 访问 | 现有内部 `exe_mem_size` | 总线 `data_sram_size` |
| --- | --- | --- |
| byte | `2'b01` | `2'd0` |
| half | `2'b10` | `2'd1` |
| word | `2'b00` | `2'd2` |

内部表示“字节/半字 one-hot，字为全零”；总线表示每次访问字节数的以 2 为底的对数。必须做转换，不能直接赋值。

```verilog
// 设计示意：内部编码 -> 总线编码
bus_size = exe_mem_size[0] ? 2'd0 :
           exe_mem_size[1] ? 2'd1 : 2'd2;
```

### 5.3 子字访问保持原来的字节通道语义

- `st.b`：`wstrb = 4'b0001 << addr[1:0]`。
- `st.h`：对齐地址低两位为 00 或 10，分别选 `0011` 或 `1100`。
- `st.w`：`wstrb = 1111`。
- byte 的写数据可以继续复制成 `{4{value[7:0]}}`；half 可以继续用 `{2{value[15:0]}}`。

例如 `st.b` 写地址 `0x1003`，值为 `0xAB`，可输出 `size=0`、`wstrb=1000`、`wdata=ABABABAB`。只有高字节车道生效。

地址低位仍表示访问字内哪个字节，不能因为底层是 32 位 RAM 就在 CPU 输出上统一清零。非对齐字/半字访问则应先产生 ALE，禁止发外部请求。

## 6. 取指端：给每笔请求留下身份

### 6.1 为什么原来的 if1_fire_r 不能继续使用

原先 `if1_fire_r` 的意思实际上是“上拍发过请求，所以本拍接口上就是该请求的指令”。随机延迟会使这个推论失效。

正确做法是：地址握手时锁存该次请求的 PC，响应时把指令数据与这个已保存的 PC 配对。不能在响应时随手读取当前 `if1_pc`，因为当前 PC 可能早已改成分支目标或异常入口。

### 6.2 先画四状态，再写寄存器

这里把 IF2 当成一个包含事务等待和指令缓存的取指槽。

| 状态 | 含义 | 可以发新请求吗 | 可以送 ID 吗 |
| --- | --- | --- | --- |
| EMPTY | 没有待响应事务，也没有缓存指令 | 可以 | 不可以 |
| WAIT | 某次取指已被接收，等待响应 | 不可以 | 不可以 |
| HAVE | PC 和指令都已缓存，等待 ID | 不可以 | 可以 |
| DROP | 旧请求已被冲刷，但还要等它的响应并丢弃 | 不可以 | 不可以 |

建议先以状态寄存器表达，不要一开始同时维护状态和多个重复含义的 valid。若仍保留 `if2_valid`，明确它表示“可交付给 ID 的指令”，而不是“外部事务尚未完成”。

```text
EMPTY --地址握手--> WAIT --数据响应并缓存--> HAVE --交给 ID--> EMPTY
                        |
                        +--收到重定向--> DROP --旧响应返回并丢弃--> EMPTY

HAVE --收到重定向，清掉缓存--> EMPTY
```

### 6.3 地址握手时保存什么

至少保存 `fetch_pc`。如果把 ADEF 检测提前，还要保存取指异常标记及其原始坏地址。

第一版可以让维护 PC 的 `IF_PC.v` 输出“下一笔尚未接收请求的地址”，由顶层取指槽管理 `req` 和状态：

```text
reset：下一笔 PC = 0x1c000000
地址握手：fetch_pc = 本次请求 PC；下一笔 PC = 本次请求 PC + 4
重定向：下一笔 PC = 重定向目标，优先级高于顺序更新
```

注意定义变化：原来的 PC、`if1_fire`、pending 分支逻辑是围绕同步 BRAM 写的，不能在新状态机之外继续各自修改 PC。应统一 PC 的唯一更新来源。

为简化边界，第一版可在 `redirect=1` 的整拍禁止新请求，下一拍再申请目标地址。因为类 SRAM 允许撤掉尚未接收的请求，这样可避免“新地址握手与重定向同拍”的一组组合情况。

### 6.4 返回指令时一定先缓存

第一版在 WAIT 收到 `data_ok` 后，无条件锁存 `inst_sram_rdata` 并进入 HAVE。下一拍及以后，ID 允许时才交付。

示意条件：

```verilog
if2_ready_go = (fetch_state == HAVE);
if2_fire = if2_ready_go && id_allowin && !redirect;
```

这有意多花一拍换取简单控制。之后如果希望减少一拍，再增加从返回端直通 ID 的旁路；直通后仍必须保留“ID 不接收就缓存”的路径。

缓存中要同时保持 PC 和指令，直到交付或被取消。`data_ok` 消失后，缓存的有效性不能随它一起消失。

### 6.5 用一个时序检查缓存

| 拍 | 状态 | `data_ok` | `id_allowin` | 应有结果 |
| --- | --- | --- | --- | --- |
| T0 | WAIT | 0 | 0 | 保持等待 |
| T1 | WAIT | 1 | 0 | 缓存返回指令，转 HAVE |
| T2 | HAVE | 0 | 0 | 缓存 PC/指令保持 |
| T3 | HAVE | 0 | 1 | 仅交付一次，转 EMPTY |

如果 T3 仍要等第二次 `data_ok`，说明把“收到过响应”这个状态丢了。

## 7. 分支、异常和返回：取消指令不能取消账目

### 7.1 重定向先统一成一个事件

可以在概念上统一：

```text
redirect = wb_redirect 或 本拍允许执行的 EXE 分支跳转
target   = wb_redirect ? (trap ? EENTRY : ERA) : branch_target
```

WB 的异常/返回优先于年轻的 EXE 分支。`ertn` 同样需要处理未完成取指请求，不能只处理异常而漏掉返回。

### 7.2 四种状态下收到重定向怎么办

| 原状态 | 本拍是否有响应 | 处理 |
| --- | --- | --- |
| EMPTY | 无 | 更新下一笔 PC，维持 EMPTY |
| WAIT | 无 | 更新下一笔 PC，转 DROP，保留旧事务记录 |
| WAIT | 有 | 旧响应当拍丢掉，转 EMPTY，不再等第二次响应 |
| HAVE | 无待响应事务 | 清掉缓存，转 EMPTY |
| DROP | 无 | 继续等旧响应；有更新的重定向则更新目标 |
| DROP | 有 | 丢掉旧响应，转 EMPTY；目标按重定向优先级保存 |

同拍既有 `data_ok` 又有 redirect 时，不能先按正常返回进入 HAVE，再让错误指令漏给 ID。状态更新表必须覆盖组合事件。

### 7.3 为什么 DROP 不能省

例子：旧 PC=A 的请求已被接收，CPU 随后跳到 B。A 的指令过五拍才回来。若冲刷时只清 `if2_valid`，然后立刻把这个响应配给 B，最终会执行“PC 是 B、指令码却来自 A”的错误组合。

DROP 保存的是“仍欠外部一次响应处理”的事实。清空逻辑流水线不等于清空外部总线。

在本讲义的一笔未完成事务方案下，一个 DROP 状态就够用。如果以后允许同时有两笔取指未返回，只丢下一笔就不够了，需要计数或逐笔元数据队列。

### 7.4 ADEF 不能因为不发请求而死锁

错误取指 PC 的低两位不为 0 时，应产生 ADEF。一个容易写出的死锁是：“发现 ADEF，所以 req=0；但 IF2 又永远等待 addr_ok/data_ok 才进入 ID”。

可采用一条内部完成路径：EMPTY 发现坏 PC，不发总线请求，直接建立包含坏 PC 的异常槽并进入 HAVE；指令码可使用明确的占位 NOP。现有 ID 通过 `id_pc[1:0]` 判断 ADEF，因此必须把原始坏 PC 传下去，并保持它的异常优先级。该槽没有总线事务，不能等待一个不会出现的响应。

不要为了让取指成功而把坏 PC 对齐后当成正常指令执行。

### 7.5 教材 br_stall 在本设计里怎么理解

教材讨论了在 ID 裁决分支时，源操作数未就绪导致错误目标被用于取指的问题。你们的分支在 EXE 裁决，ID 已有数据相关停顿，所以不必机械复制同名 `br_stall`。

你们应保证：分支源操作数在 `id_fire` 时正确；EXE 确定跳转时，已取回和未返回的年轻指令都被取消。顺序预取可以存在，只要错误路径严格丢弃。

## 8. 数据端：EXE 等接收，MEM 等完成

### 8.1 给 MEM 增加“这条指令需要响应”的字段

现有 MEM 保存了 `mem_res_from_mem`，能识别 load，但没有同样明确地保存“正常 store 也要等待响应”的字段。

建议新增 `mem_wait_resp` 或等价字段。它的定义是：**这条指令进入 MEM 时，已经成功发出一笔外部事务，因此必须等一次响应。**

这个定义优于简单地写 `load || store`，因为有 ALE、已有同步异常的 load/store 并未发外部请求，不应等待响应。

### 8.2 EXE 发请求的基本条件

第一版可采用以下保守条件，变量名为示意：

```verilog
exe_is_mem = exe_res_from_mem || exe_mem_we;
exe_mem_normal = exe_is_mem && !exe_final_exc;

data_req = resetn && exe_valid && exe_mem_normal
        && !older_redirect_pending
        && !mem_valid;  // 第一版仅 MEM 空时申请，刻意限制并行度

data_addr_fire = data_req && data_sram_addr_ok;
```

这里使用 `!mem_valid` 是为了省去“旧事务本拍返回、新请求本拍接收”的重叠控制。它比用 `mem_allowin` 更保守：即使 MEM 的普通 ALU 指令本拍即将离开，也等下一拍再发请求。

这不是最终性能方案。如果改为 `mem_allowin`，还要用独立的事务占用条件证明不会提前接收第二笔数据请求，不能只替换一个条件。

### 8.3 按指令类型定义 EXE 的完成条件

| EXE 指令 | `ready_go` 的含义 |
| --- | --- |
| 普通 ALU、乘法、CSR 等 | 本级所需计算已完成 |
| 正常 load/store | 本次地址握手成功 |
| 已带异常的 load/store | 不请求内存，可以带异常继续后传 |
| 除法 | 计算完成事件已出现，或结果已经缓存 |

示意结构：

```text
若本指令有异常：允许向后传递异常（不依赖外部握手）
否则若为访存：ready_go = data_addr_fire
否则若为除法：ready_go = div_done 或 div_result_valid
否则：ready_go = 1
```

然后沿用：`exe_fire = exe_valid && exe_ready_go && mem_allowin`。由于本方案发请求时 MEM 必为空，正常访存地址握手与其进入 MEM 可以在同一个时钟沿发生，不会出现“请求被接收但没有地方存指令上下文”。

`older_redirect_pending` 为 1 时，年轻正常访存可以等待后续冲刷；它不应为了继续流动而发请求。

### 8.4 怎样保证每条访存只发一次

地址握手沿：

1. MEM 锁存这条指令的 PC、目的寄存器、地址低位、访存大小等上下文。
2. MEM 锁存 `mem_wait_resp=1`。
3. EXE 原指令离开或被下一条指令替换。
4. 下一拍 MEM 非空，禁止发第二笔数据请求。

因此第一版不必在 EXE 再放一个重复含义的“已接收”位。若以后允许 EXE 在请求被接收后仍驻留，才必须增加 `addr_accepted`，避免 req 每拍重复握手。

### 8.5 MEM 的完成条件

当前 `wb_allowin=1`，因此可以保持数据端无额外响应缓存的简单路径：

```verilog
// 设计示意：只有确实发过外部请求的指令才等响应
mem_ready_go = !mem_wait_resp || data_sram_data_ok;
mem_fire = mem_valid && mem_ready_go && wb_allowin;
```

正常 load/store 在 MEM 等响应；ALU、乘法、CSR、异常指令和 `ertn` 不等待总线响应。

load 响应到来并 `mem_fire` 时，沿用现有 `wb_sram_rdata <= data_sram_rdata` 的保存路径，WB 再抽取/扩展。没有 `data_ok` 时不得提前将 load 交给 WB。

这里能不加数据缓存，依赖 **WB 始终接收**。如果以后 WB 也有停顿，就必须缓存 `data_ok` 带来的数据和完成状态；否则会遇到与取指缓存相同的问题。

### 8.6 store 为什么也必须停在 MEM

考虑 `st.w` 后面紧跟 `ld.w`。store 地址握手后还欠一次写响应。如果 store 立即退出 MEM，后面的 load 就可能把 store 的 `data_ok` 当作自己的读响应，并读取无效数据。

所以 `mem_wait_resp` 必须覆盖正常 store。写响应的 `rdata` 可以忽略，但这笔完成事件必须被消耗。

另外，本地 RAM 包装器在地址请求接收时就可能把写请求送进 RAM。`data_ok` 是完成通知，不是可以等到它出现才决定是否允许写入的最后关口。

### 8.7 异常与数据响应的边界

当前异常来源在 ID/EXE 检测，MEM/WB 不再新增异常；而数据请求已经检查自身异常和更老的重定向。因此可以采用教材提到的严格发请求策略，使 load/store 发出后不会再被更老异常取消。

这个结论有前提，不能靠清空 valid 来“实现”：请求接收时，必须已经排除了所有可能取消它的更老异常/返回。年轻 EXE 分支的冲刷只影响前端，不会取消更老的 MEM 访存。

建议验证断言：若 `wb_redirect && mem_valid && mem_wait_resp` 成立，应调查它是否违反了上述设计前提。以后若增加 MEM 阶段才发现的异常，或放宽请求门控，就必须重新设计数据端的旧响应丢弃机制。

## 9. MEM 能停以后，全流水线都要重新审视

### 9.1 分支不能先清掉自己，再等待 MEM

当前 `exe_br_taken` 由 `exe_valid` 和分支条件产生；EXE 的 valid 又在 `exe_br_taken` 时清零。原来 MEM 恒接收时，分支自身能同拍进入 MEM，这条写法容易成立。

exp14 中若老 load 在 MEM 等待，年轻 `bl/jirl` 驻留 EXE：如果仍立即产生 `exe_br_taken`，EXE 被清掉，但 `exe_fire=0`，分支自身没有进入 MEM，link 寄存器写回就丢了。

第一版的简单解法是把“条件已成立”和“本拍真正执行跳转事件”分开：

```verilog
branch_condition = ...; // 原有比较结果与分支类型组合
branch_redirect = exe_fire && !exe_final_exc
               && !older_redirect_pending && branch_condition;
```

让这条事件负责前端冲刷和 PC 重定向。分支只有在自身确实向 MEM 转移的那一拍才触发。它会晚一些，但不会重复，也不会丢 `bl/jirl` 的 link 写回。

接线时要检查没有组合环：普通分支的 `exe_ready_go` 应独立于 `branch_redirect`。不要先用分支事件决定 ready，再用 ready 决定分支事件。

### 9.2 除法 done 只有一拍，MEM 不一定刚好接收

当前除法路径使用 `div_done` 直接置 `exe_ready_go`，完成后清 `div_doing`。在 MEM 长时间等待的情况下可能出现：

```text
老 load 在 MEM 等待
年轻 div 在 EXE 运算
div_done 出现，但 mem_allowin=0
下一拍 div_done 消失，div 仍未离开 EXE
```

如果只看完成脉冲，结果就可能丢失；若 `div_doing` 已清而 EXE 仍持有 div，还可能重复启动同一条除法。

解决方向：增加 `div_result_valid` 和结果缓存。

- 一条除法在 EXE 生命周期内只启动一次。
- `div_done` 时保存恢复符号后的结果，或者保存原始商余数并保证恢复符号所需上下文仍有效。
- `div_result_valid=1` 后，即使 `div_done=0`，EXE 仍应认为计算完成。
- 直到这条除法 `exe_fire` 或被冲刷，才能清除其结果有效状态。
- 新指令进入 EXE、复位和完成/消费同拍的更新优先级要明确。

还要保留现有“有老异常时不启动年轻除法”的约束。若扩展到运行中的除法可被取消，应处理除法器迟到的完成脉冲，不能把它给下一条 div。

### 9.3 load-use 停顿应随等待时间自然延长

你们 `control.v` 在 MEM 存在相关 load 时持续拉高 `id_stall`，且排除了 MEM load 前递。这一结构可以继续使用：load 等多久，消费者就停多久，直到 WB 提供结果。

教材“把 MEM 前递有效改成结果可交付”是针对有 MEM load 前递的结构。你们第一版不必新增这种前递，只需确认：

- `mem_valid` 在等待期间保持。
- `mem_dest`、`mem_res_from_mem` 等字段保持。
- `mem_hit` 不能因为没有 `data_ok` 就失效，否则消费者会读到旧寄存器值。
- `data_ok` 到来时不提前让消费者锁存尚未进入 WB 的 load 数据。

等待中的独立 ALU 指令可能进入 EXE 并在那里驻留，这是正常反压，不应解释成整个 CPU 每一级都立刻冻结。

### 9.4 其它需要复查的状态

| 对象 | 审查问题 |
| --- | --- |
| EXE/MEM 级间数据寄存器 | 是否仅在 `exe_fire` 时改写？MEM 等待时是否保持？ |
| 乘法结果寄存器 | `mul_prod_mem` 能否在 MEM 堵住时保持旧指令的结果？ |
| CSR | `csr_inflight` 是否仍持续阻塞到 CSR 真正完成？ |
| WB debug | 没有有效提交时，写使能是否为 0？不能每等一拍重复报一次写回 |
| 稳定计数器/定时器 | CPU 停顿期间仍按时钟工作；不能因为流水线等内存就冻结计时 |
| 异常上下文 | PC、ECODE、BADV 等是否仍和对应指令一起保持和流动？ |

## 11. 怎样验证，怎样读波形

### 11.1 不要只用完整 func 发现最基本的握手错误

先用很短的程序和可控制延迟的存储器模型，让每个场景只暴露一个问题。验证模型也要遵守类 SRAM 约束，例如 `addr_ok` 的生成不能依赖 `req`；响应不能凭空出现，读写都必须有且仅有一次响应。

| 场景 | 延迟/程序安排 | 检查重点 |
| --- | --- | --- |
| 取指地址等 5 拍 | `addr_ok` 连续为 0，然后置 1 | PC 不提前推进，没有虚假的 if1_fire |
| 取指返回等 7 拍 | 地址已接收，延后 `data_ok` | WAIT 不被当作有效指令；不重复取相同 PC |
| 指令回来但 ID 堵住 | 先造成 load-use 或除法反压 | 一次响应缓存后可交付，不能等第二次响应 |
| 等取指时发生分支 | 旧请求已接收，再重定向 | 旧响应只进入 DROP 消耗路径 |
| 返回与重定向同拍 | 精确安排 `data_ok` 和跳转 | 旧响应当拍丢弃，不能多等一笔或漏进 ID |
| 连续两次重定向 | 例如分支后又有更老 WB 异常 | 最新且高优先级的目标不丢，旧事务数量仍正确 |
| load 地址迟迟不接收 | EXE 多拍保持 load | `addr/size` 和上下文稳定，不提前进入 MEM |
| store 后紧跟 load | 写响应故意延迟 | store 的响应不会被认作 load 返回 |
| load-use/load-to-branch | load 返回延迟变化 | 消费者不读取旧值，分支最终方向正确 |
| MEM 等待，EXE 是 bl/jirl | 老 load 等待，link 指令驻留 EXE | 分支自身不丢，link 只写回一次 |
| MEM 等待超过除法时长 | 老 load 等 50 拍以上，年轻 div 运算 | done 后缓存，既不重启也不丢结果 |
| ALE 和 ADEF | 未对齐访存/取指 | 无非法总线请求，异常最终正常提交 |
| syscall/ertn 配合等待 | 取指响应在冲刷之后返回 | 旧响应被消耗，新入口/返回地址正确 |
| 字节和半字访问 | 覆盖 4 个 byte 偏移和 2 个 half 偏移 | size、wstrb、写数据和 WB 抽取一致 |

### 11.2 波形按三组看

**总线组**：两端的 `req / addr_ok / data_ok / addr / size`，数据端再加 `wr / wstrb / wdata / rdata`。

**流水线组**：`if2/id/exe/mem/wb` 的 valid、PC，`id_stall`，`exe_ready_go`、`mem_ready_go`、`exe_fire`、`mem_fire`，以及取指状态和缓存内容。

**取消与长运算组**：`wb_redirect`、分支事件、重定向目标、`older_redirect_pending`、`div_doing`、`div_done`、除法缓存有效位。

先找第一个错误提交 PC，再反查它来自哪次响应，最后查响应对应哪次地址握手。不要从错误出现之后几十拍的混乱状态倒猜原因。

### 11.3 用计数器证明没有漏账

在测试平台分别给两端累计：

```text
accepted += req && addr_ok
responded += data_ok     // 按模型约定，每个有效响应只计一次
outstanding = accepted - responded
```

复位时清计数；如果 CPU 和存储器共同复位并清空事务，统计也从新一轮复位重新开始。不要在仅仅发生分支/异常冲刷时清外部事务计数。

本讲义基础方案应满足：`0 <= outstanding <= 1`。DROP 的响应也属于 responded，只是没有交付为有效指令。

这些验证计数器放在 testbench 中即可，不必综合进 CPU。

### 11.4 几条特别有价值的检查

- WAIT/DROP 没有收到响应前，指令端不接受第二笔请求。
- IF2 已缓存且 ID 不接收时，PC 和指令保持。
- MEM 需要响应而 `data_ok=0` 时，`mem_fire=0`。
- 正常 store 必须先等到写响应，才允许下一笔数据事务。
- `exe_final_exc` 或 `older_redirect_pending` 有效时，不接受新的数据请求。
- 一次除法开始后，在当前除法离开 EXE 前不会再次启动。
- `bl/jirl` 的 link 结果与一次有效分支提交对应。

测试平台是按有效寄存器写回事件推进参考记录，再比较 PC、目的寄存器和写数据，不要求随机等待下的每个时钟周期都与参考 CPU 一样。每个功能点 PASS 后，还要看最终 `Test end!` 和 `----PASS!!!`，中途没有报错不等于完整通过。

### 12.3 三类随机延迟怎么选

本地 `confreg.v` 的随机寄存器实际为 23 位。复位时采样种子，其中：

```text
no_mask     = 种子低 16 位等于 0x00FF
short_delay = 种子低  8 位等于 0xFF
```

可以从以下完整宏值开始测试，保持高位非零，避免伪随机寄存器进入全零锁死状态：

| 宏值示例 | 对应模式 | 说明 |
| --- | --- | --- |
| `{7'b1010101, 16'h00FF}` | 无随机掩码等待 | `no_mask=1`，适合先排除基础错误 |
| `{7'b1010101, 16'h01FF}` | 短延迟 | 本地当前默认值，`short_delay=1`、`no_mask=0` |
| `{7'b1010101, 16'h0001}` | 长延迟类 | 两个模式位都为 0，暴露更多等待组合 |

模式由复位期间的种子决定，不能在运行中把当前 LFSR 的低位重新当成模式选择。每类再选多个不同低位值，记录实际宏值、测试结果和日志。修改宏后要重新编译/展开仿真并复位，不能只继续原来的运行。

不要把无随机等待解释为 CPU 可以不看握手。即使这一模式下响应很快，也仍然使用相同的协议。

### 12.4 综合和上板放在最后

随机仿真通过后，才进入综合、实现和下载。旧报告的 100 MHz 正时序只代表旧设计，新的握手反压链可能改变关键路径。

保守方案可能出现 `ID stall -> 前端允许 -> req` 一类长组合链。应根据新的实现报告定位，不能为了沿用旧主频而恢复“取指常开”。若优化性能，优先增加明确的缓冲和局部状态，再重新验证事务数量、冲刷和时序。

有硬件时，复位期间切换拨码开关覆盖无延迟、短延迟、长延迟类种子。若只在某种子失败，把该种子带回仿真复现；无硬件时，记录跳过上板，不把功能仿真称为上板通过。

## 13. 常见故障与定位顺序

| 现象 | 优先怀疑 | 首先看什么 |
| --- | --- | --- |
| PC 递增，但连续指令码相同 | 重复接受请求、PC/响应配对错误 | 每个 `req && addr_ok` 对应的 PC |
| 偶尔跳转后马上 INE | 旧取指响应被当成新目标指令 | DROP、fetch_pc、响应与 redirect 同拍处理 |
| 指令回来后永久不动 | 没保存完成状态，仍等第二次 data_ok | HAVE/缓存 valid 是否被错误清除 |
| store 后的 load 读到随机值 | 写响应被错认成读响应 | `mem_wait_resp` 是否包含 store |
| ALE 测试死锁 | 异常访存没发请求，却仍等待响应 | 异常路径的 EXE/MEM ready |
| 分支跳了，但 ra/link 不对 | MEM 等待时清掉了 EXE 分支自身 | branch 事件与 `exe_fire` 是否对齐 |
| load 长延迟后除法错误或变慢 | done 未缓存、同一 div 反复启动 | div 启动次数、完成缓存、MEM 允许 |
| 只在某些种子失败 | 同拍事件、缓存覆盖、未完成事务漏记 | 首个失败前后的握手和状态转移 |
| 仿真一开始端口错误 | 仍使用 soc_bram 接口或引用了旧源码 | CPU 实例端口和实际工程文件列表 |
| 功能正常但实现时序失败 | 握手链拉长、扇出上升 | 新的最差路径，不能套旧报告结论 |

排错时按“外部事务是否记对 -> 返回数据是否存好 -> 流水线是否在正确时刻消费 -> 最终写回是否正确”的顺序。不要一开始就修改 ALU 或译码掩盖握手错误。

## 14. 自检与报告素材

### 14.1 写代码前，先口头回答

1. `addr_ok=1` 而 `req=0` 时，有没有新事务？
2. 地址握手后连续 20 拍没响应，CPU 应保存哪些内容？
3. ID 不接收，但指令响应只来一拍，怎样不丢？
4. 为什么清空 `if2_valid` 不等于取消取指事务？
5. 为什么 store 也要等响应？
6. 已发生 ALE 的访存为什么不能等 `data_ok`？
7. 为什么旧的 `exe_br_taken` 会在 MEM 阻塞时丢掉 link？
8. 为什么除法完成需要从一个脉冲变成可保持的状态？

参考答案：1 无；2 请求身份和流水上下文，不能重复请求；3 缓存；4 外部仍会返回；5 消耗属于自己的写响应、防止串事务；6 没发请求就没有响应；7 分支尚未转移却清了自身；8 下游不一定刚好接收。
